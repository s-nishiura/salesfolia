# フェーズ1: システム基盤構築 要件定義

本フェーズでは、システム全体の土台となるインフラ・アーキテクチャ・認証認可の基盤を構築する。
ビジネスロジックの実装（フェーズ2以降）をスムーズに進めるための準備フェーズとなる。

## 1. 開発環境・技術スタック
- **フレームワーク**: Ruby on Rails
- **データベース**: PostgreSQL (マルチテナント時のスキーマ分離や柔軟なJSONB検索を考慮し推奨)
- **フロントエンド**: Hotwire (Turbo + Stimulus)
  - 専用業務機ライクな「キーボード操作完結」を実現するため、必要なJS処理はStimulusで制御する。
- **CSSフレームワーク**: Tailwind CSS など (開発速度とカスタマイズ性を重視)

## 2. マルチテナント環境
複数の企業（テナント）が1つのシステムを共有するB2B SaaSモデル。
- 企業間でデータが混ざらないよう、論理的な分離を徹底する。
- 全ての主要テーブルは `tenant_id` を持ち、スコープによるグローバルなアクセス制限（例: `default_scope` やマルチテナント用Gemの利用）を基本とする。
- **データ構造の分離**: `Tenant` はシステム管理上の論理的な枠組みとして扱い、実際の企業情報（会社名、住所、連絡先など）は分離して `Company` テーブルに保持する。

## 3. 認証・ユーザー管理機能
ユーザーがシステムにログインするための機能。
- **認証ライブラリ**: `rodauth` (Rodauth-Rails) を採用。
- **アカウント構造 (テナント完全分離・高セキュリティモデル)**:
  - `Tenant` (システム契約の単位)
  - `Company` (企業情報)
  - `Account` (ログイン認証用。Rodauth標準に合わせ、メアドやパスワードを保持。必ず `tenant_id` を持つ)
  - `AccountProfile` (アカウントに紐づく実際の氏名・所属などの個人情報を保持。必ず `tenant_id` を持つ)
  - 伝帳法などの法的要件を鑑み「安全性」を最優先とし、**各アカウントはテナント内に完全に閉じる設計**（複数企業を兼任するユーザーは企業ごとに別々のアカウントを作成・ログインする）とする。

## 4. 権限管理 (認可モデル)
今後のモジュール拡張（営業、倉庫、経理など）に耐えうる、詳細な権限管理システム。
- **Group (担当グループ)**: 「営業部」「倉庫管理チーム」などの論理グループ。各グループに対して権限（Role）を付与する。
- **Account (個人設定)**: 各アカウントはグループに所属しつつ、個別に権限設定を上書き（オーバーライド）可能とする。
- **権限の優先順位**: グループの設定 ＜ 個人の設定

## 5. UI/UXのベースライン（キーボード操作対応）
フェーズ0の段階で、アプリケーション全体のレイアウトや操作の共通基盤を確立する。
- フォーム入力時の「Enterキーで次の項目へ移動」するベースJavaScript（Stimulusコントローラー）の実装。
- ショートカットキー（例: `Ctrl + S` で保存）を受け付ける基盤の用意。

## 6. 法的コンプライアンス・監査基盤 (安全性第一)
電子帳簿保存法およびインボイス制度への対応を見据え、初期段階から厳密なデータ管理基盤を導入する。
- **変更履歴 (Audit Log)**: 伝票やマスタデータの「誰が・いつ・何を・どう変更したか」の履歴を全てテナントごとに保存する（`paper_trail` 等の導入）。
- **論理削除 (Soft Delete)**: トランザクションデータや重要マスタにおいては物理削除を原則禁止し、削除フラグによる論理削除（`discard` 等の導入）を標準とする。
- 認証情報から履歴データに至るまで、すべてのデータを `tenant_id` の壁で完全に隔離することで、他社データへの混入リスクをゼロにする。
