# ADR-0003: フロントエンド技術とUIライブラリの選定

## ステータス
採用（Accepted）

## 背景と課題
既存の専用業務機からの移行先としての最大のUX要件は、「マウスを一切使わず、Enterキーでフォーカスを移動しながら高速に伝票入力ができる」ことである。
近年流行しているSPA（Single Page Application）を採用すればリッチな操作性を実現しやすいが、Railsエコシステムとの乖離が生じ、開発スピードや保守性が低下する懸念があった。
また、UIコンポーネントライブラリとしてどのツールを採用するかも選定が必要であった。

## 決定事項
以下のフロントエンドスタックを採用する。

1. **基本アーキテクチャ**: `Hotwire (Turbo + Stimulus)`
   - SPAは採用せず、Rails標準のサーバーサイドレンダリング(SSR)を活かす。
   - 高度なキーボード制御やフォーカス移動は、`Stimulus` コントローラーを用いて局所的にDOMを操作・フックして実現する。
2. **UIコンポーネント管理**: `ViewComponent`
   - RailsのViewをコンポーネント化し、再利用性とテスト容易性を高める。
3. **CSSフレームワーク**: `Tailwind CSS` + `DaisyUI`
   - ユーティリティファーストなTailwindをベースとし、汎用的なUIパーツはDaisyUIを利用する。
   - ※ 検討に上がった `reactionview` については、コンポーネント間にデバッグ用の `span` タグが自動挿入されてしまう仕様により、HTMLの階層構造が変わってしまう。DaisyUIは親子関係のDOM構造に依存したCSS設計となっているため、スタイルが正しく当たらなくなる相性問題が確認され、採用を見送った。

## 結果と影響
### メリット
- Railsエコシステムにフルノリできるため、APIとフロントエンドを分離するオーバーヘッドがなく、開発速度が最大化される。
- JavaScriptの記述量を最小限に抑えつつ、必要な箇所（キーボード操作）だけにリソースを集中できる。

### デメリット
- HotwireやStimulus特有のライフサイクル（Turbo Driveによる画面遷移時のDOMキャッシュ等）を理解した上でJSを記述する必要がある。
