# ADR-0002: マルチテナントアーキテクチャと認証の完全分離

## ステータス
採用（Accepted）

## 背景と課題
本システムは既存の専用業務機をリプレイスする B2B SaaS-ERP である。
中小企業においては、経営者が複数会社を兼任したり、外部の税理士が複数企業のデータを閲覧したりするユースケースが存在する。
そのため、当初は「1つのアカウントでログインし、システム内でテナント（企業）を切り替える構成（ワークスペース切り替え型）」を検討した。

しかし、本システムは販売管理・会計データという極めて秘匿性の高い情報を扱う。また、電子帳簿保存法やインボイス制度への対応として、厳密な「変更履歴（Audit Log）」と「論理削除」の要件が求められる。
共通アカウントモデルを採用した場合、ユーザーが複数テナントを跨ぐことで、監査ログのスコープ管理が複雑化し、万が一のバグによる「他社データへの混入・漏洩リスク」が高まる懸念があった。

## 決定事項
「安全性（コンプライアンス）」を最優先とし、**テナントごとにアカウントを完全に独立させる構成（従来型SaaS型）** を採用する。

1. `Account` モデルは必ず `tenant_id` を保持し、テナント内に完全に閉じる。
2. ログイン画面のURLはサブドメイン（例: `slug.salesfolia.dev`）等によってテナントごとに分離する。
3. すべてのトランザクションデータおよび履歴データ（PaperTrail等）も `tenant_id` の壁で隔離する。

## 結果と影響
### メリット
- セキュリティと実装がシンプルになり、他社データへの混入リスクが物理的・論理的にゼロになる。
- データの変更履歴（誰がいつ変更したか）がテナント内で完全に完結するため、監査対応が容易になる。
- テナントごとに独自のセキュリティ要件（SAML認証の強制など）を将来的に組み込みやすくなる。

### デメリット
- 複数企業を兼任するユーザーは、企業ごとに別々のアカウント（メアド・パスワード等）を作成し、別々にログインする必要がある。
  - ※ UXの低下は許容し、セキュリティとコンプライアンスを優先した結果のトレードオフである。
